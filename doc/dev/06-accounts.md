# 6. 계정과 데이터베이스 운영

로그인하면 플랜이 **계정에 저장**됩니다. 집 컴퓨터에서 만든 플랜을 사무실에서
이어서 볼 수 있고, 브라우저 기록을 지워도 사라지지 않습니다.

---

## 어떻게 저장되나요

플랜은 **브라우저에 먼저 저장되고, 그다음 계정으로 올라갑니다.**

```
편집 → 브라우저 저장소에 즉시 저장 (예전과 동일)
          ↓  1.2초 뒤
       계정(서버)으로 올림
```

이 순서에는 이유가 있습니다.

| 상황 | 결과 |
| --- | --- |
| 인터넷이 끊김 | 편집은 그대로 됩니다. 연결되면 이어서 올라갑니다. |
| 올리는 중에 창을 닫음 | 브라우저에 남아 있다가 다음에 들어올 때 올라갑니다. |
| 서버가 잠깐 죽음 | 작업이 멈추지 않습니다. |

화면 위쪽 칩이 지금 상태를 알려 줍니다.

| 칩 | 뜻 |
| --- | --- |
| `저장 중` | 계정으로 올리는 중 |
| `저장됨` | 계정에 반영 완료 |
| `저장 안 됨` | 올리지 못함. 브라우저에는 남아 있습니다. |

## 여러 기기에서 쓰기

같은 계정으로 로그인하면 플랜이 따라옵니다. 같은 플랜을 두 기기에서 동시에
고치면 **나중에 고친 쪽이 남습니다.**

한 기기에서 플랜을 지우면 다른 기기에서도 사라집니다. 되살아나지 않습니다.

## 로그인 전에 만든 플랜

로그인 기능이 생기기 전에 만든 플랜은 브라우저에 남아 있습니다.
처음 로그인하면 화면 위에 이런 안내가 뜹니다.

> 로그인 전에 이 브라우저에서 만든 플랜이 **N개** 있습니다.
> [내 계정으로 가져오기] [버리기]

**가져오기** 를 누르면 계정으로 올라갑니다. 누르기 전까지는 서버로 올라가지
않습니다 — 한 컴퓨터를 여러 명이 쓸 때 남의 플랜이 딸려 올라가면 안 되기
때문입니다.

`버리기` 는 되돌릴 수 없습니다. 헷갈리면 그냥 두세요. 안내는 계속 남아 있습니다.

## 로그아웃하면 플랜이 사라져요

정상입니다. 플랜은 계정(서버)에 있고, 브라우저에 있던 사본만 지운 것입니다.
같은 계정으로 다시 로그인하면 그대로 돌아옵니다.

이렇게 하는 이유는 **한 컴퓨터를 여러 사람이 쓸 때** 앞사람의 플랜이 뒷사람에게
보이거나, 뒷사람 계정으로 올라가 버리는 것을 막기 위해서입니다.

---

## 계정 만들기

가입 정책은 배포한 사람이 환경변수로 정합니다.

| 설정 | 결과 |
| --- | --- |
| 아무것도 없음 | **가입 닫힘.** 공용 테스트 계정으로만 들어옵니다. |
| `SIGNUP_CODE=...` | 그 초대 코드를 아는 사람만 가입 |
| `ALLOW_SIGNUP=1` | 누구나 가입 |

기본이 "닫힘" 인 이유는, 배포된 주소는 누구나 열 수 있는데 AI 생성은 **주인의 API
키로 돌기 때문**입니다. 아무나 가입하면 요금이 주인에게 갑니다.

### 공용 테스트 계정

지인에게 보여 줄 때 쓰는 계정입니다. `TESTER_EMAIL` 과 `TESTER_PASSWORD` 를
모두 넣으면 **첫 로그인 때 자동으로 만들어집니다.** 따로 준비할 것이 없습니다.

환경변수의 비밀번호를 바꾸면 다음 로그인 때 그 비밀번호로 바뀝니다.

> 여러 사람이 같은 계정을 쓰면 **플랜을 함께 보고 함께 고칩니다.** 각자 자기
> 플랜만 갖고 싶다면 초대 코드를 알려 주고 각자 가입하게 하세요.

---

## 저장소

`DATABASE_URL` 이 가리키는 **Postgres** 입니다. Supabase, Neon, RDS 등 무엇이든
됩니다 — 특정 서비스에 묶인 코드가 없습니다.

`DATABASE_URL` 이 **없으면** PGlite(Postgres 를 WebAssembly 로 빌드한 것)가
`.pglite` 폴더에 데이터를 넣습니다. 설치할 것 없이 로컬 개발이 되고, 같은 SQL 이
그대로 돌기 때문에 로컬에서 확인한 동작이 배포에서도 같습니다.

배포에서는 반드시 `DATABASE_URL` 을 넣으세요. 서버리스는 인스턴스가 매번
새로 뜨므로, 파일에 저장하면 다음 요청에서 사라집니다.

### 표 구조

```sql
users (id, email, name, password_hash, created_at)
plans (id, user_id, title, data jsonb, updated_at, created_at)
       primary key (user_id, id)
```

- 플랜 본문은 `data` 한 칸에 통째로 들어갑니다. 화면이 쓰는 모양 그대로라
  옮기는 과정에서 어긋날 일이 없습니다.
- 기본키가 `(user_id, id)` 인 이유: 플랜 ID 는 브라우저가 만들어서 전역으로
  고유하지 않습니다. `id` 만 기본키로 두면 다른 사람과 번호가 겹칠 때 저장이
  조용히 실패합니다.
- 표는 서버가 뜰 때 `create table if not exists` 로 만들어집니다. 따로 실행할
  마이그레이션 명령이 없습니다.

## 보안

| 항목 | 방식 |
| --- | --- |
| 비밀번호 | scrypt 해시로만 저장. 원문은 어디에도 남지 않습니다. |
| 세션 | HMAC-SHA256 으로 서명한 httpOnly 쿠키. 스크립트가 읽을 수 없습니다. |
| 유효기간 | 30일 |
| 남의 플랜 | 모든 질의가 `user_id` 로 걸립니다. 주소를 알아도 볼 수 없습니다. |
| AI 생성·에이전트 | 로그인해야 부를 수 있습니다. |

`AUTH_SECRET` 이 세션 서명 열쇠입니다. **배포에 이 값이 없으면 로그인이 아예
동작하지 않습니다** — 개발용 기본값으로 넘어가면 누구나 세션을 위조할 수 있어
일부러 막아 두었습니다.

이 값을 바꾸면 모든 사용자가 로그아웃됩니다. 계정과 플랜은 그대로입니다.

### Supabase 를 쓸 때

프로젝트를 만들 때 **`Enable Data API` 와 `Automatically expose new tables` 를
꺼 두세요.** 이 앱은 접속 문자열로 직접 붙으므로 REST API 가 필요 없습니다.
켜져 있으면 `users` 표(비밀번호 해시가 든 표)가 인터넷에서 열립니다.

이미 만들었다면 **Project Settings → API** 에서 끌 수 있습니다.
