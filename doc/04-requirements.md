# 4. 요구사항과 기능 정리

## 프로덕트 요구사항 (PRD)

**이 서비스가 무엇이고 누구를 위한 것인가**를 정하는 문서입니다.
뒤에 만들 모든 문서가 이걸 기준으로 삼기 때문에, 여기가 흐리면 나머지도 흐려집니다.

### 두 가지 보기

상단의 **`문서 보기` / `편집`** 버튼으로 오갑니다.

- **문서 보기** — 읽기 좋게 정리된 모습. 보고할 때나 인쇄할 때
- **편집** — 칸을 채우는 모습. 고칠 때

그 아래 목차 칩을 누르면 해당 부분으로 바로 내려갑니다.

### 10개 항목

| # | 항목 | 무엇을 적나 |
| --- | --- | --- |
| 1 | 제품 개요 | 이 제품이 무엇이고 누구에게 어떤 가치를 주는지 |
| 2 | 배경 및 문제 정의 | 왜 지금 이게 필요한지 |
| 3 | 핵심 목표 | 목표와 그걸 어떻게 판단할지 |
| 4 | 타겟 유저 | 어떤 사람인지, 무엇이 필요하고 무엇이 불편한지 |
| 5 | **사용자 역할** | 일반 회원·판매자·관리자 등 |
| 6 | 사용 환경 | 어떤 기기·브라우저를 지원하는지 |
| 7 | 핵심 가치 | 이 제품이 지키려는 것 |
| 8 | 성공 지표 | 무엇이 얼마나 되면 성공인지 |
| 9 | 범위 | 이번에 만들 것 / 안 만들 것 |
| 10 | 제약사항 | 일정·인력·정책상 어쩔 수 없는 것 |

> **5번 사용자 역할은 특별합니다.** 여기 적은 역할이 정보구조도에서 "이 화면은 누가
> 볼 수 있나" 를 정할 때 선택지로 나옵니다. 역할을 빠뜨리면 나중에 화면마다 권한을
> 지정할 수가 없습니다.

> **9번 범위의 '안 만들 것'을 꼭 채우세요.** 개발 견적을 받을 때 가장 많이 싸우는
> 지점입니다. 미리 적어 두면 "이것도 되는 줄 알았는데요" 를 막을 수 있습니다.

각 항목 제목 옆의 말풍선 아이콘으로 메모를 남길 수 있습니다.

## 기능명세서 (FS)

**필요한 기능을 빠짐없이 적고, 각 기능이 화면에서 어떻게 동작하는지**를 적는 문서입니다.
개발자가 가장 많이 보는 문서이기도 합니다.

### 3단 구조

```
요구사항          "회원이 산책 메이트를 찾을 수 있어야 한다"
  └ 기능          "위치 기반 메이트 검색"
      └ 상세 기능  "반경 3km 내 회원을 거리순으로 보여준다"
```

| 단계 | 답하는 질문 |
| --- | --- |
| **요구사항** | 무엇이 필요한가 |
| **기능** | 그걸 어떤 기능으로 푸는가 |
| **상세 기능** | 그 기능이 화면에서 어떻게 동작하는가 |

---

### 세 가지 보기

같은 내용을 세 방식으로 봅니다. **어느 쪽에서 고치든 나머지에 바로 반영됩니다.**
위쪽의 `마인드맵` `리스트` `표` 로 전환합니다.

| 보기 | 이럴 때 |
| --- | --- |
| **마인드맵** | 전체 구조를 한눈에 보고 **빠진 곳을 찾을 때** |
| **리스트** | 한 요구사항을 파고들며 **차근차근 채울 때** |
| **표** | 우선순위와 상태를 **한 번에 훑고 고칠 때** |

검색과 필터는 세 보기에 똑같이 적용됩니다.

#### 마인드맵 보기

왼쪽부터 `PRD → 요구사항 → 기능 → 상세 기능` 순서로 펼쳐집니다.

- 요구사항마다 **색이 다르고**, 그 아래 기능들이 같은 색을 물려받습니다.
  덩어리를 눈으로 구분하기 좋습니다.
- 오른쪽 끝의 번호(`1.1.2`)는 순서입니다.
- 항목 앞의 점은 작업 상태입니다. (회색 작성전 · 주황 작성중 · 파랑 검토중 · 초록 확정)
- 항목을 누르면 **오른쪽에 편집창**이 열립니다.
- 빈자리의 **`핵심 기능 추가` · `상세 기능 추가`** 를 누르면 그 자리에 바로 만들어집니다.
- 오른쪽 위 `-` `100%` `+` 로 크기를 조절합니다.

#### 리스트 보기

세 칸으로 나뉩니다.

| 칸 | 내용 |
| --- | --- |
| 1칸 | 요구사항 목록. 고르면 2칸이 바뀝니다 |
| 2칸 | 그 요구사항의 기능들. `›` 를 누르면 상세 기능이 펼쳐집니다 |
| 3칸 | 고른 항목의 편집창 |

각 칸 오른쪽 위 `+` 로 새로 추가합니다.

#### 표 보기

요구사항과 기능을 한 표로 펼칩니다. **우선순위와 상태를 표에서 바로 바꿀 수 있어서**
전체를 정리할 때 가장 빠릅니다.

기능 번호를 누르면 리스트 보기로 넘어가면서 그 항목이 열립니다.

---

### 편집창에서 하는 일

#### 요구사항

제목, 설명, 분류, 우선순위를 고칩니다.

> 요구사항을 삭제하면 **그 아래 기능과 상세 기능이 전부 함께 지워집니다.**

#### 기능

기능명, 설명, 우선순위, 상태, 상위 요구사항을 고칩니다.
이 기능이 **어느 화면에 들어가 있는지**도 함께 보여 줍니다(읽기 전용).
아래쪽 **연결된 상세 기능** 카드를 누르면 그 상세 기능으로 넘어갑니다.

#### 상세 기능

여기가 가장 중요합니다. **개발자와 QA가 그대로 보고 일하는 부분**입니다.

| 칸 | 이렇게 적으세요 |
| --- | --- |
| **수행 주체** | 누가 하는 동작인지 — `회원`, `관리자` |
| **사전 조건** | 이 동작이 가능하려면 어떤 상태여야 하는지 — `로그인되어 있어야 함` |
| **기본 흐름** | 사용자와 시스템의 행동을 번갈아 — `① 회원이 검색 버튼을 누른다 ② 시스템이 반경 3km 목록을 보여준다` |
| **예외 처리** | 잘못될 수 있는 경우 — `위치 권한이 없으면 안내 후 설정으로 보낸다` |
| **인수 조건** | QA가 그대로 테스트할 수 있는 문장 — `위치 권한 허용 상태에서 검색 시 3km 내 회원만 나온다` |
| **연결 화면** | 이 동작이 일어나는 화면 (정보구조도에서 만든 화면 중에서 고름) |

> **예외 처리를 비워 두지 마세요.** 개발 단계에서 가장 많이 되묻는 부분입니다.
> 권한 없음 · 네트워크 실패 · 결과 없음 정도만 적어 두어도 크게 도움이 됩니다.

### 우선순위

| 값 | 뜻 |
| --- | --- |
| **P0** | 없으면 출시 불가 |
| **P1** | 1차 범위 |
| **P2** | 여유가 되면 |
| **P3** | 나중에 |

> 개발 견적이나 일정을 뽑을 때 **P0 만 먼저 세어 보세요.** 그게 최소 출시 범위입니다.
